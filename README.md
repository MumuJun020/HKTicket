# HKTicket

面向香港快达票（[hkt.hkticketing.com](https://hkt.hkticketing.com)）的多账号抢票辅助工具。

用 Flask 提供本地 Web 控制台，通过 [比特浏览器](https://www.bitbrowser.cn/) 的本地 API 驱动多个指纹浏览器窗口，
让每个抢票人在各自独立的浏览器环境（独立 cookie、指纹、可配独立 IP）里并发抢票。

> ### 使用须知
>
> - **仅供个人学习与自用**，使用前请自行确认符合目标站点的服务条款与当地法律。
> - 程序**只执行到「确认订单」锁单为止，不会自动付款**，也没有实现任何支付相关代码。
> - **验证码必须由人工完成**，程序不做任何验证码识别或绕过。
> - 账号密码以**明文**保存在本机 `data/accounts.json`（该目录已被 `.gitignore` 排除）。
>   请勿把 `data/` 同步到网盘、打包分发，或在共享电脑上使用本工具。

## 功能

| 模块 | 说明 |
|---|---|
| 抢票人管理 | 增删改查、批量删除，账号密码存本地；每人绑定一个独立浏览器窗口 |
| 登录态检测 | 通过站点接口精确判断谁已登录，已登录的自动跳过，不做无谓的重复登录 |
| 一键登录 | 并发拉起窗口、填账号密码、点登录；**验证码由人工完成** |
| 登录态清除 | 换人复用窗口时自动清；也可手动批量清除 |
| 票务解析 | 一个请求拿全所有场次/票档/售罄状态，不需要登录、不点「立即购买」 |
| 抢票配置 | 每人各自配置场次、票档、张数，支持批量填充，改动自动保存 |
| 立即 / 定时抢票 | 多账号并发；定时精确到秒；支持暂停、恢复、停止 |
| 蹲回流票 | 可以配置当前已售罄的票档，程序持续轮询，等有人退票放出时抢入 |
| 实时日志 | SSE 推送，倒计时和蹲票状态原地刷新不刷屏 |

## 二、配置教程

### 2.1 配置比特浏览器

**第一步：安装并登录客户端**

到 [bitbrowser.cn](https://www.bitbrowser.cn/) 下载安装，注册并登录。**客户端必须全程保持运行**，关掉它本工具就连不上了（页面会提示「连不上比特浏览器（127.0.0.1:54345）」）。

**第二步：确认本地 API 已开启**

比特浏览器的本地 API 默认监听 `127.0.0.1:54345`，一般不用额外设置。验证一下：

```bash
curl -s -X POST http://127.0.0.1:54345/browser/list -H 'Content-Type: application/json' -d '{"page":0,"pageSize":10}'
```

返回 `{"success":true,"data":{"list":[...]}}` 就说明通了，`list` 里就是你的窗口。
如果连接被拒绝，说明客户端没运行；如果返回 `token 失效`，说明客户端没登录。

**第三步：创建窗口**

在客户端里按抢票人数创建窗口（10 个人就建 10 个窗口）。建议：

- **给窗口起有辨识度的名字**，比如直接用抢票人的名字，后面绑定时好认。
- **每个窗口配独立代理 IP**。这是用指纹浏览器的主要意义 —— 十个账号从同一个出口 IP 打，风控很容易关联。代理在窗口的「代理设置」里配。
- **内核选择**上没有特殊要求，默认即可。

**第四步（推荐）：关掉「同步标签页」**

窗口设置里的 `syncTabs` 如果开着，比特浏览器会在关闭窗口时记下当时所有标签页，下次打开原样恢复 —— 自动化每跑一轮都留下页面，标签页会越积越多（实测重开后直接恢复出 4 个页面）。

本工具在每次一键登录前会自动帮你关掉这个开关，所以**你不手动改也可以**，这里只是说明它为什么会被改动。

### 2.2 配置抢票人

启动服务：

```bash
cd HKTicket && PORT=5055 ./venv/bin/python run.py
```

打开 <http://localhost:5055>，在左侧「抢票人」卡片点**新增**，填四项：

| 字段 | 说明 |
|---|---|
| 备注 | 显示用的名字，比如「张三」。日志里用它标识来源 |
| 账号 | 快达票登录邮箱 |
| 密码 | 明文保存，一键登录时程序自动填入 |
| 浏览器窗口 | 下拉选择，列表从比特浏览器实时拉取 |

> **一个窗口只能绑一个抢票人**，程序会强制校验。两个人绑同一个窗口的话，
> 并发登录时两个任务会连到同一个浏览器操作同一个页面，互相覆盖对方填的账号密码 ——
> 表现就是「两个人的密码进了同一个框，另一个窗口没人动」。

点「窗口」按钮可以刷新窗口列表。密码是**明文显示**的，这是刻意的：本工具单机自用，遮成 `******` 反而看不出哪个账号配错了。

### 2.3 环境变量（可选）

| 变量 | 默认 | 作用 |
|---|---|---|
| `PORT` | 5000 | 服务端口。macOS 上 5000 被 ControlCenter（AirPlay）占用，建议用 5055 |
| `KEEP_DATA=1` | 关 | 跳过启动清理，沿用上一轮的抢票人和配置（调试用） |
| `KEEP_EVENT=1` | 关 | 只保留上次解析的活动信息，抢票人照常清空 |

## 三、使用教程

整个流程分四步，从左到右、从上到下走一遍即可。

### 第 1 步：一键启动并登录

点右上角**「一键启动并登录」**。程序会：

1. 批量清除需要重新登录的窗口（判断规则见下方[登录态清除](#登录态清除)）
2. 并发拉起所有窗口，各自导航到登录页
3. 自动填入账号密码并点击登录

**然后轮到你**：如果弹出验证码，切到对应窗口手动完成。程序会等待（默认最长 180 秒），登录成功会在日志里报「登录成功」。

顶部显示 `3 / 5 已登录` 这样的实时状态，点「刷新状态」可以重新检测。

> 「刷新状态」只查**已经打开**的窗口，不会为了查状态弹出新窗口。

### 第 2 步：解析票务信息

在「票务解析」框里填活动详情页链接，或者直接填 projectId：

```
https://hkt.hkticketing.com/#/allEvents/detail?projectId=1589126120000181
```

点**解析**。这一步是**纯 HTTP 请求，不需要登录、不会弹出任何浏览器窗口**，几百毫秒返回。

解析完会列出全部场次和票档，包含价格和售罄状态。点「明细」可以展开看完整列表。

### 第 3 步：配置每个人抢什么

在「配置每个人抢什么」表格里，给每个抢票人分别选：**场次**、**票档**、**张数**。

- 改动**自动保存**，不需要点保存按钮。
- 上方有批量下拉，可以「批量设置场次」后点「应用到全部」，再单独微调个别人。
- **已售罄的票档也可以选**（显示为虚线边框）。这是为了蹲回流票 —— 有人退票时票会重新放出，程序会一直轮询到抢中为止。

### 第 4 步：开抢

「开抢」区的参数：

| 参数 | 建议值 | 说明 |
|---|---|---|
| 重试间隔（秒） | 2 ~ 4 | **不要调太小**，见下方警告 |
| 最大尝试（0 = 不限） | 0 | 蹲回流票时保持 0 |
| 自动勾选条款并确认订单 | 勾选 | 锁单，**不付款** |
| 有人抢到就停掉其他人 | 按需 | 多账号各抢各的时不要勾 |

> ⚠️ **重试间隔别调小。** 站点按 IP 限流，实测密集请求几十次就会被掐连接，
> 被限之后该窗口连正常浏览都进不去，反而彻底抢不了。程序内置了限流识别和指数退避，
> 但前提是你别一开始就把间隔设成 0.1 秒。

两个按钮：

- **立即抢票** —— 马上开始
- **定时抢票** —— 先在「定时开抢」里选好时间（精确到秒），到点自动开始

开抢后按钮变成**暂停 / 停止**，日志区实时显示每个人的进度。抢到后程序会自动勾选条款、提交确认订单完成锁单，然后**停下来等你手动付款**。

### 登录态清除

用于「窗口比人少，需要复用窗口」的场景。程序按一张归属表（`data/window_owner.json`）判断：

| 情况 | 处理 | 场景 |
|---|---|---|
| 记录是同一个人 | **不清**，直接复用登录态 | 他抢完这场接着抢下一场，省掉重过验证码 |
| 记录是别人 | **清除后重新登录** | 10 个人 5 个窗口，第二批复用第一批的窗口 |
| 没有记录 | **清除后重新登录** | 程序刚重启（启动会清空归属表），或全新窗口 |

因为启动时归属表会被清空，所以效果就是：**程序重启后所有人都需要重新登录**。

也可以手动清：在「抢票人」卡片点「选择」进入批量模式，勾选后点**「清除登录态」**。

> 清除会关闭窗口并清掉 Cookie 和本地存储，下次登录需要重新处理验证码。

## 四、启动行为与数据

**每次启动会清空上一轮数据**：抢票人、抢票配置、窗口归属、活动信息全部清零，保证每次打开控制台都是干净的。

为什么在启动时清而不是退出时清：退出钩子在 `kill -9`、进程崩溃、断电时都不会执行，靠不住；启动时清是必然执行的，效果一样。

数据文件都在 `data/`（已被 `.gitignore` 排除）：

| 文件 | 内容 |
|---|---|
| `accounts.json` | 抢票人：账号、**明文密码**、备注、绑定窗口 |
| `event.json` | 解析留存的活动票务信息 |
| `plans.json` | 每个账号抢什么的配置 |
| `window_owner.json` | 窗口归属：某个窗口上次登录的是谁 |

调试时想保留数据，用 `KEEP_DATA=1` 启动。

## 六、设计要点

改动前请先读对应模块的注释，下面几条都是踩坑之后固化下来的。

### 一个窗口只能绑一个抢票人

重复绑定时，多个并发任务会连到同一个浏览器、操作同一个页面，互相覆盖对方填的账号密码。
存数据和实际登录两处都做了校验。

### 售罄判断看 `saleState` 和 `sellOut`，不要用 `canAddCart`

```
场次在售 = saleState == 2        （3 = 售罄/停售）
票档可买 = 场次在售 且 sellOut != True
```

`canAddCart` 是「能否加入购物车」不是「能否购买」。曾经用它当可买性标志，
导致票档明明可选、「下一步」也亮着的活动被误报成「全部售罄」。

票档级 `sellOut` 单独用也不够：整场 `saleState=3` 时，有的票档 `sellOut` 仍是 `false`，但一张都买不了。

### 解析走接口，不点「立即购买」

`GET https://rest-sig.imaitix.com/api/pro/project?projectToken=<id>&reqType=1&langType=1`

实测服务端只校验两个头：`referer: https://hkt.hkticketing.com/` 和 `site: m`。
不需要 cookie、不需要登录。看着像动态签名的 `hecate` 实测**不校验**（删掉、置零、重放、跨活动都照样返回数据），
它是前端埋点字段。

好处：不需要登录；有风控时点「立即购买」可能直接进不去；不占用浏览器窗口；
数据比页面更全（限购数量等字段 UI 上未必显示）。

### 请求节流是硬性要求

纯 API 连打（不加载页面资源、没有埋点，光秃秃的接口请求一次接一次）在风控眼里是教科书式的爬虫特征。
**实测二三十次这样的请求就足以让整个出口 IP 被站点拉黑**，被封后该 IP 连正常浏览都是 `ERR_CONNECTION_CLOSED`，持续很久。

代码里的三道防护不要拆：接口调用强制间隔、解析全程只发一个请求、抢票循环默认 2~4 秒并带指数退避。

### 只读用接口，写操作全程走 UI

下单链路（选场次→选票档→调数量→提交→勾条款→确认订单）有状态、有顺序依赖，必须全程 UI 自动化：
用接口直接建单的话页面状态会脱节；有些参数是上一步接口返回的，跳步拿不到；
而且风控看的是行为轨迹，凭空冒出一个下单请求比慢一点更容易被拦。

### 清除登录态必须先关窗口

**窗口开着时，清除接口会返回 `success: true` 但什么都不清。**
实测往 localStorage 写标记，不关窗直接清 cache + cookie，两个接口都报成功，reload 后标记原样还在。
不能靠返回值判断清没清干净，只能靠「先关窗」这个前提。

另外两个接口的参数形状不一样，容易写错：

```
/browser/cookies/clear   {"browserId": "<id>"}   单数、字符串
/cache/clear             {"ids": ["<id>"]}       复数、数组
```

cookie 和 cache 两个都要清：cookie 里是会话，但站点在 localStorage 的 `ACCOUNT_INFO` 里
还存了 email、phone、userToken —— 只清 cookie 会把上一个人的身份留在窗口里。

### 比特浏览器的同步接口要走 `asyncio.to_thread`

`openBrowser` 等函数内部是同步的 `requests` 调用，一次要几秒。直接在协程里调会卡住事件循环，
让 `asyncio.gather` 的并发退化成串行。实测 2 个窗口：阻塞调用 4.9s、`to_thread` 2.7s，
窗口越多差距越大。

## 八、常见问题

**连不上比特浏览器 / 窗口列表是空的**

客户端没启动或没登录。启动客户端并登录后点「窗口」重新拉取。
用 [2.1 第二步](#21-配置比特浏览器)的 curl 命令可以确认接口通不通。

**一键登录很慢**

正常情况下窗口是并发拉起的。如果明显慢，检查是不是很多窗口都需要清除登录态 ——
清除需要关闭窗口并等待进程退出。这个等待是一次性的，不随窗口数增长。

**登录后提示已登录，但其实是别人的账号**

不应该发生，程序按窗口归属表校验。如果遇到，手动「清除登录态」后重新登录，并提 issue。

**解析报「接口没返回活动数据」**

确认 projectId 正确、活动没下架。如果站点所有页面都打不开（`ERR_CONNECTION_CLOSED`），
是 IP 被限流了，换 IP 或等一段时间。

**抢票时报「未找到匹配场次」**

多半是配置串台了：解析过 A 活动、配好方案，之后又解析了 B 活动。
重新解析当前活动并重新配置即可（程序有校验，会拦下这种情况）。

**端口被占用**

macOS 上 5000 端口默认被 ControlCenter（AirPlay）占用，用 `PORT=5055` 换一个。

## 已知限制

- 选择器只针对 hkticketing 写死，不做通用票务网站解析。
- 不做购票人实名信息存储和自动填表 —— 这些信息应该已经在各自的账号里。
- 真正的多窗口并发抢票（如 10 人 5 窗口）尚未在实际场景中充分验证。
